# pronunciation: OCP -> "O C P"; L.O.C.K. -> "lock"; MEK -> "meck"; SED -> "S E D"; CSP -> "C S P"; EMEA -> "E M E A"; 2026 -> "twenty twenty-six"
The security problem begins at the end of a drive's first service life.

A storage device leaves its supplier, enters a data center, and accumulates customer data. When the device is retired, the operator must decide whether it can leave the controlled environment. Customer data cannot leave with it. The operator therefore needs high confidence that every usable copy of every Media Encryption Key is gone.

Self-encrypting drives support cryptographic erase. In principle, deleting a media key makes its ciphertext permanently unreadable. In practice, a cloud operator may not trust an erase performed entirely by complex drive firmware. A firmware bug, a compromised signing key, an incomplete key binding, or recoverable key material can turn a successful status code into false assurance.

The conservative answer has been physical destruction. That protects confidentiality, but it also prevents reuse, refurbishment, and component recovery. The result is avoidable electronic waste.

O C P lock creates another branch in that lifecycle. It isolates keys inside a hardware-rooted management block and ties all active media keys to epoch material that can be zeroized and reported. At the twenty twenty-six O C P E M E A Summit, the presenters emphasized the operator's goal: reason about the drive in isolation, without proving that every customer, platform, or backup copy of an external key has disappeared.

That doesn't make every failed device recoverable. If a controller is too damaged to perform and report the required zeroization, the same assurance isn't available. But when the protected operation succeeds, cryptographic erase can support reuse instead of automatic destruction.
