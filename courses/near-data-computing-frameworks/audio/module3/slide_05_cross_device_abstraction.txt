# pronunciation: PNM -> P N M; PIM -> P I M; DPU -> D P U
An abstraction becomes useful when it preserves the differences that software needs while offering a common way to express work. The draft maps computational storage resources onto processing in memory, processing near memory, and data processing units. Treat that mapping as a proposal to test across implementations.

Several ideas can recur: discover a resource, identify a supported function, reserve or refer to operand memory, request execution, and establish completion. But the source and sink of the data can differ. Storage work may refer to persistent data and device buffers. A memory-oriented operation may use a bank-local region or device-attached memory. A D P U may operate on an ongoing network stream.

That is why the draft proposes a generalized source and sink description, additional memory attributes, and richer function arguments. A single vocabulary is helpful only if it can express those cases without making unsupported guarantees. A P I M mechanism should not be assumed to use the same launch or completion path as every other device.

The two detailed proof-of-concept examples both use P N M. A useful community contribution is therefore another walkthrough: describe the same conceptual lifecycle for computational storage, a P I M device, or data in flight. Identify exactly where the proposed shared model fits and where it needs a new capability, restriction, or example.
