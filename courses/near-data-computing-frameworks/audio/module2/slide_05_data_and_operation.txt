# pronunciation: HDF5 -> H D F five; ONNX -> Onyx
An address or handle tells software where to refer to data. It does not fully describe what those bytes mean. A device may need the element type, dimensions, layout, stride, and alignment before it can interpret an operand correctly. It also needs an agreed meaning for the requested operation, its arguments, and its output.

The draft discusses open formats as a way to make these descriptions usable across software boundaries. Apache Arrow describes in-memory columnar data and associated interchange structures. H D F five organizes self-describing datasets and metadata for persistent scientific data. These serve different roles; neither should be treated as a universal device execution contract.

Onyx represents machine-learning models and their operations. Substrait describes relational computations in a portable form. They help explain why a representation of the computation is different from the physical layout of its data. We use those definitions as supporting background; the draft's Onyx and Substrait subsections still need further development.

For the filtering example, naming a buffer is not enough. Software must agree on the record schema, predicate semantics, output layout, and any supported types. For a tensor operation, dimensions and strides can determine which elements are actually read. A shared format can reduce avoidable conversions when the implementations support it. It does not automatically provide zero-copy execution, device compatibility, or correct synchronization. Keep representation, operation meaning, and execution guarantees separate in your review.
