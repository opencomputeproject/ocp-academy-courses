Hitless firmware maintenance depends on a controlled lifecycle, not a single successful command.

Inspect the remote image information, then start the download. Transfer the firmware in blocks and check every result. If a block transfer fails, abort the download and perform cleanup rather than continuing with an incomplete image.

After all blocks arrive, the complete-download command validates that stage. A failure, such as a bad image checksum, means the download has not succeeded. Do not proceed to activation.

Once completion succeeds, run the new image and verify its behavior. Only then commit the running image as the default for future resets. This distinction between run and commit is central to knowing what the module will do now and after a reset.

The local module carries these operations to the chosen remote partner over the in-band interface. Maintain that partner identity throughout the sequence.

Hitless capability still needs deployment verification. Check actual traffic continuity, command status, recovery behavior, and the maintenance policy before relying on the workflow in service.
