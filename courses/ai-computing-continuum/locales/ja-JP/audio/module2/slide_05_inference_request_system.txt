# pronunciation: AI -> エーアイ; GPU -> ジーピーユー; KV -> ケーブイ
ここでは、通常1つのサイト内にある推論サービングデプロイメントを詳しく見ます。ディスアグリゲーションは、機能とリソースプールを分離する設計です。それだけでリクエストがサイト間ワークフローになるわけではありません。

リクエストはまず、推論対応ゲートウェイと配置コントローラーに到着します。そこで、モデル、ロード済みアダプター、サービス優先度、応答目標を特定します。コントローラーは、キュー深度、利用可能なアクセラレーター、メモリー負荷、ローカルトポロジー、データ位置、ポリシー、サービスヘルスを評価し、ワーカープールを選びます。

プロンプト処理、つまりプリフィルは、プリフィルプールで実行され、最初のケーブイステートを作ります。入力コンテキストが長くなるほど、大きなコンピュートを必要とします。モデルウェイトとリトリーバルデータも、ワーカーから利用できなければなりません。

プリフィルとデコードが別のプールを使う場合、ケーブイステートをサービングファブリックで転送します。途中では、高帯域のアクセラレーターメモリー、ホストメモリー、別のキャッシュ階層に置かれることがあります。ケーブイステートは推論の別フェーズではありません。プリフィルが生成し、デコードが利用する作業コンテキストです。

デコードは、応答を反復的に生成します。各ステップで蓄積済みステートを読み、次のトークンを作り、キャッシュを拡張します。このフェーズは、演算性能よりメモリー帯域やメモリー容量に制約される場合があります。

アテステーションとポリシーは、どのリソースを利用可能とするかを制御します。テレメトリは、キュー、メモリー負荷、エラー、電力、サービスヘルスを配置コントローラーへ返し、次のルーティング判断に反映します。

プールを分けると干渉を抑え、フェーズごとに適したリソースプランを選べます。ただし、ケーブイステートの転送にはコストがあります。Time to First Tokenとトークンレイテンシの目標内に収める必要があります。

これらの機能をサイト間に広げる場合は、別途スケールアクロスまたはリーチアクロスとして設計します。そのサイト間の問いは、次のモジュールで扱います。
