Consider three examples. A firmware command parser receives input from a less trusted source. You want the review to examine how that input is validated and whether it can corrupt memory or bypass authorization. That's a code and architecture concern associated with Scope one.

Now consider a system that separates application processing from a security function. The question is whether that separation really protects privileged operations and sensitive assets. A deeper trust-boundary assessment brings the emphasis of Scope two into view.

Finally, consider a long-lived device secret used by a hardware trust anchor. If an attacker can manipulate the device physically, the review may need to examine fault injection or information leakage through side channels. That's the additional emphasis of Scope three.

The examples show how to ask for the right depth. They don't replace the threat model or the provider's scoping judgment. Start with the asset and the attacker's capabilities, then agree the assessment needed.
