# pronunciation: CMIS -> C M I S; CDB -> C D B; I2C -> I squared C; SONiC -> sonic; PMD -> P M D; VDM -> V D M; DDMI -> D D M I; SNR -> S N R; PAM4 -> PAM four; MPI -> M P I; FEC -> feck; BER -> B E R; LOS -> L O S; LOL -> L O L; DSP -> D S P; SDK -> S D K; API -> A P I
A telemetry request needs three pieces of context: target, side, and port.

Target selects the local module or a remote partner. Side selects the host-facing electrical interface or the media-facing optical interface. Port identifies the relevant datapath, which matters when one module connects to several partners.

Command eight thousand one hex returns the telemetry for that selection. Software prepares the request, triggers it, polls status, and reads the successful reply.

The reply identifies whether the target is online and accessible. It includes the rating and lowest-category bitmap, module serial identity, link-down count, uptime, flags, signal-quality measurements, environmental values, and feck information.

Some reply fields summarize the worst lane rather than listing every lane independently. Optical power includes minimum and maximum values. Keep that aggregation context when moving from a port summary to a detailed investigation.

An offline target is not a healthy target with zero-valued metrics. Report accessibility explicitly. The common workflow remains the same for local and remote requests, but the endpoint and interface context must remain attached to the evidence.
