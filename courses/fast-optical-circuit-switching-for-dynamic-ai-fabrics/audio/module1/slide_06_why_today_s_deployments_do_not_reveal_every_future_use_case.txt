The paper calls out a use-case paradox. Many attractive applications for very fast optical switching depend on supporting capabilities that are not yet widely available together. Yet deployments naturally concentrate on problems that existing equipment and software can solve today.

This can make the future look like a faster version of current practice. If today's switch is mainly used to set up a topology between jobs, it is easy to assume that faster switching has little value. But a fabric that can change connectivity within a communication cycle could support a different operating model.

That possibility does not remove the engineering work. Fast receiver recovery, predictable actuation, scalable scheduling, and suitable endpoint behavior must develop alongside the switching mechanism. Small experimental port counts can also limit which workload patterns a prototype can explore.

The useful response is to distinguish two questions. What can we deploy with the current ecosystem? And what application becomes plausible if a specific system constraint is removed? State the missing capability and how it would be tested. This avoids dismissing emerging uses because they do not fit today's systems, while also avoiding the assumption that an interesting component demonstration is already a deployable fabric.
