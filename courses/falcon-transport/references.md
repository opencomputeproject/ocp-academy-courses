## MRC and SUE-T overlap

| Existing coverage | Overlap with Falcon | Treatment in this course |
|---|---|---|
| [MRC, Module 1 Why MRC](https://github.com/opencomputeproject/ocp-academy-courses/blob/main/courses/multipath-reliable-connection-mrc/course.json): tail latency, congestion, failures, limitations of conventional RC. | Motivation for reliable multipath transport. | Limit to a short opening recap. Refer learners to MRC for the training-fabric motivation. |
| MRC, Module 2 Inside MRC: entropy values, SRv6, out-of-order placement, independent SACK/NACK, NSCC, trimming, ECN and failure bypass. | Multipathing, selective loss repair and feedback. | Teach Falcon's RSN/PSN separation, BACK/EACK, two receive/ack states, RACK–TLP, Swift and four-flow Max-Open-Window scheduling. Do not relabel MRC SACK as Falcon EACK or transfer MRC EV counts, SRv6 routing or failure timings into Falcon. |
| MRC, Module 3 Deploying MRC: multi-plane fabrics, APIs, scale results and constraints. | Deployment context and transport comparisons. | Provide a course reference. Omit API instruction, deployment recipes and comparative benchmark claims from the Falcon core. |
| [SUE-T, Module 1 From XPU Transactions to Ethernet Transport](https://github.com/opencomputeproject/ocp-academy-courses/blob/main/courses/sue-t-ethernet-transport-for-xpu-scale-up-systems/course.json): transport boundaries, transaction flow, Delivery/Operational ACK and completion. | Distinguishing arrival, acknowledgement and completion. | Use a brief boundary comparison in Module 1. Falcon's Push Data ACK follows target ULP acknowledgement; do not introduce SUE-T's mode names as Falcon features. |
| SUE-T, Module 2 Efficient Packets on a Lossless Fabric: work-conserving packing, RODL/PDC state, expected-sequence acceptance, GoBackN option and lossless service. | Reliability and resource/forward-progress reasoning. | Contrast one sequence-gap case with Falcon's retained out-of-order packets and selective repair. Keep SUE-T packing, traffic-class requirements and GoBackN in its own course. |
| SUE-T, Modules 3 and 4: AXI mapping, identifiers, 4096-byte cases, four completion points and memory visibility. | Potential temptation to expand Falcon into a ULP integration course. | Link as related learning only. Exclude AXI, RDMA/NVMe mappings and application-level memory visibility guarantees from Falcon. |

MRC and SUE-T are related courses, not mandatory prerequisites. Falcon Module 1 supplies the transport model needed by Modules 2 and 3. Shared concepts receive a short recap so an experienced learner can enter without completing both adjacent courses.

The MRC source currently presents an NSCC-focused implementation story; the reviewed 2026 MRC presentation explicitly distinguishes the transport feedback framework from per-connection congestion policy. The Falcon comparison will identify mechanisms by their own specification and avoid turning an implementation example into a universal claim.

## Source interpretation issues to preserve during scripting

- The contents pages are stale. Cite the actual PDF page and section, verified against the page footer.
- Keep v1.1 changes separate from v1.2 additions. The base-header Version field is 1; 1.2.0 is the specification revision.
- The general receive-window description on p. 64 and the detailed boundary check on p. 84 use different edge wording. The outline does not assess that ambiguous edge; verify with the detailed rule and specification owners before making a boundary-condition exercise.
- The prose on p. 94 and fractional fields in the RUE tables describe NIC-window precision differently. Teach the control roles and the explicitly defined per-flow fractional fabric behavior; do not write a quiz on ncwnd's representation.
- The requirement for exact pull-response length in normal processing coexists with the explicit zero-length pull CIE case and the error summary's shorter-data note. Keep error exceptions in context and avoid a universal payload-length quiz.
- Section 12 specifies a 256-position transmit cap for performance with a v1.1 receiver; its v1.0 row says compatible without assigning a numeric cap there. Do not silently extend the v1.1 number to every older peer.
