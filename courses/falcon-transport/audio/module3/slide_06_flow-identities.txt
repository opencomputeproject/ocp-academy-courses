Falcon can distribute a single connection across up to four flows. Each flow has a twenty-bit flow label that participates in equal-cost multipath hashing, commonly called E C M P. The lower two bits identify Falcon's path: zero zero, zero one, one zero, and one one. The flow labels must give the active paths distinct path identifiers.

Those paths do not create four independent reliable connections. Request and data delivery state remains shared at the connection level. A global delivery bitmap can describe packets that used different paths. Meanwhile, the transmitter saves the path identifier associated with each packet, and congestion measurements and fabric windows are maintained per path. This is why one acknowledgment can advance shared delivery state while generating several path-specific accounting updates.

Keep two scheduling questions separate. Connection scheduling chooses which eligible connection gets service. The path scheduler chooses a flow label for a packet of that connection after the applicable aggregate transmit gates have passed. Path selection does not override those gates, erase the two sequence windows, or change the connection's ordered-delivery contract.

The low two bits provide stable association, not a physical route certificate. A flow label influences E C M P hashing; different labels do not prove that packets traverse disjoint physical links. Later, Protective Load Balancing may change the route-selection portion of a label while preserving those path-identifier bits. The saved packet-to-path association is essential: when delivery feedback arrives, Falcon credits the path used by that packet, rather than assuming all reported packets used the path represented by the acknowledgment's congestion metadata.
