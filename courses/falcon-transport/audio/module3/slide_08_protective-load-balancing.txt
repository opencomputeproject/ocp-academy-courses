Multipathing and Protective Load Balancing answer different questions. The path scheduler distributes packets among current flows. Protective Load Balancing, or P L B, decides when sustained congestion warrants changing a flow label to seek another route.

The decision has three stages. At an acknowledgment event, compare smoothed delay with the configured delay target multiplied by the configured P L B multiplier. Count how many acknowledged packets reflect congestion within the measurement round trip. If their fraction meets the configured congestion threshold, that round trip counts as congested. Count consecutive congested round trips; reaching the configured persistence threshold triggers a reroute attempt. A round trip below the congestion threshold resets the consecutive count. The animation names these thresholds rather than inventing deployment defaults.

A reroute changes the flow label's route-selection bits while preserving its low two path-identifier bits. The connection continues with the same path identity for accounting. A new label asks E C M P for a potentially different route; it does not guarantee physical diversity, a recovery time, or a throughput gain. This sustained-congestion mechanism is distinct from the failure-exclusion behavior described in the related M R C course.

Compatibility also shapes the operating mode. The version one point two sender-side scheduler is compatible with a version one point one receiver because the receiver behavior is unchanged. With a version one point zero peer, multipathing must be disabled, and compact congestion signaling is incompatible. These limits remain even when the local endpoint implements the newer scheduler. Evaluate the peer and the fabric together: a local feature does not establish an end-to-end capability.
